### 배운 것 / 함정

- **처리 지연은 이벤트마다 다르게 보일 수 있다.** 같은 날 발생한 `lead_form_start`는 보이는데 `generate_lead`는 0. "이벤트가 안 들어온다"고 단정하기 전에 실시간 보고서로 수집 자체를 먼저 확인한다 (오늘 실시간에서 8건 확인됨).
- **자동 이벤트와 커스텀 이벤트의 이중 측정.** 향상된 측정의 `form_start`(8)와 우리 `lead_form_start`(11)가 함께 잡힌다. 기준 이벤트를 측정 기획서에 명시해야 보고서마다 숫자가 달라지는 혼란을 막는다. 우리 기준: `lead_form_start`.
- **탐색 분석의 이벤트 선택창에는 수집된 이벤트가 곧바로 뜬다.** 관리 → 이벤트 목록(24h 지연)보다 빠르다. 이벤트 이름 오타 확인용으로 유용.
- **BigQuery 적재를 SQL 파일로 관리**하면 (`sql/00_load_crm.sql`) 콘솔 업로드 UI를 거치지 않고 재실행·버전 관리가 된다. GitHub raw 파일을 콘솔에서 바로 불러와 실행하는 흐름을 썼다.

1~3단계 숫자가 바뀐 것은 9/28 데이터 재처리. 5단계는 여전히 0.

### 원인 추적

1. 5단계 조건은 `generate_lead` 단일 이벤트, 매개변수 조건 없음 → 정의 오류 아님.
2. `generate_lead` 이벤트는 7건 처리됨 → 수집/처리 지연 아님.
3. 개방형 퍼널로 바꾸면 5단계에 **2명**(desktop 1, mobile 1)이 잡히지만, 4단계 → 5단계로 이어진 사람은 0명.
4. 보고 ID 설정은 "혼합됨/관찰됨" 계열 = **user_id가 있으면 user_id를 사람 식별 기준으로 우선 사용**.
5. 사이트는 시승 신청 제출 순간에 `customer_id`를 만들어 `user_id`로 붙이고(`site/assets/app.js` pushIdentity), `generate_lead`는 그 뒤 감사 페이지에서 발생한다.

**가설**: 폼 시작까지의 이벤트는 익명 기기 ID로, `generate_lead`는 user_id로 식별되어 GA4 탐색 분석이 두 구간을 **다른 사람**으로 집계한다. 그래서 닫힌 퍼널에서는 4→5 연결이 끊기고, 개방형에서만 5단계에 바로 들어온 소수가 보인다.

**검증 방법 (둘 중 하나)**:
- GA4 관리 → 보고 ID를 "기기 기반"으로 잠시 바꾸고 같은 퍼널을 다시 본다. 데이터는 바뀌지 않고 집계 기준만 바뀌므로 되돌릴 수 있다. 4→5가 이어지면 가설 확정.
- BigQuery 내보내기 도착 후 `user_pseudo_id` 기준으로 `lead_form_start`와 `generate_lead`를 같은 사람이 했는지 직접 조회한다 (`sql/01_web_funnel.sql`이 이미 `user_pseudo_id` 기준이라 GA4 UI와 다른 숫자가 나올 것으로 예상).

### 배운 것 / 함정

- **"이벤트가 0"은 세 가지가 섞인 문제일 수 있다**: 수집 안 됨 / 처리 안 됨 / 사람 식별 기준 때문에 연결이 안 됨. 실시간(수집) → 이벤트 수(처리) → 퍼널(연결) 순서로 좁혀 간다.
- **user_id를 중간에 붙이는 사이트는 퍼널 해석에 주의.** CDP 현업에서 로그인/신청 시점에 ID를 부여하는 구조가 일반적이므로, GA4 UI 퍼널 숫자와 BigQuery(`user_pseudo_id`) 숫자가 다를 수 있음을 처음부터 전제한다.
- **GA4 상단 검색창은 빠른 계산기다.** "이벤트명 이벤트 수 지난 7일"처럼 물으면 보고서를 찾지 않고 숫자를 준다.
- **GA4 딥링크는 계정 ID(`a…p…`) 형식이어야 열린다.** `#/p556171914/...`은 홈으로 리다이렉트된다.
- **탐색 분석은 자동 저장된다.** 토글을 만지면 그대로 저장되니 확인 후 원래대로 되돌린다 (개방형 토글 원복 완료).

### 가설 검증 결과 — 보고 ID를 "기기 기반"으로 바꿔 같은 퍼널 재계산 (확정)

관리 → 데이터 표시 → 보고 ID에서 "모두 표시" → 기기 기반 → 저장 → 확인 대화상자("혼합 ID 사용을 중지하시겠습니까?")에서 확인. 탐색 분석은 같은 질문이면 이전 결과를 재사용하므로 "경과 시간 표시" 토글로 재계산을 강제했다.

| 단계 | 혼합됨(user_id 우선) | 기기 기반 | 기기 기반 완료율 |
|---|---|---|---|
| 1 방문 | 46 | 45 | 84.4% |
| 2 라인업 조회 | 34 | 38 | 50% |
| 3 모델 상세 | 14 | 19 | 57.9% |
| 4 폼 시작 | 6 | 11 | 54.5% |
| 5 시승 신청 완료 | **0** | **6** (desktop 4, mobile 2) | - |

- 5단계 6명 = 9/28 시뮬레이션 리드 6건. 가설 확정: `user_id`를 신청 완료 시점에 붙이면 GA4 혼합/관찰 ID는 폼 시작(익명)과 완료(user_id)를 다른 사람으로 센다.
- 2~4단계도 늘어난 이유: 리드가 된 사람들의 중간 단계 이벤트가 user_id 쪽 "사람"으로 빠져나가지 않고 기기 기준으로 한 사람에 모였기 때문.
- 단계 간 경과 시간(11.7초 / 3.8초 / 7.0초 / 3.4초)은 시뮬레이터 속도라 해석 의미 없음.
- 확인 후 보고 ID는 원래 값 "혼합됨"으로 되돌림. 데이터에는 영향 없음(집계 기준만 바뀜).

**현업 적용 포인트**: Toyota CDP처럼 로그인/신청 시점에 고객 ID를 부여하는 사이트에서 GA4 UI 퍼널이 "완료 0"으로 보이면, (1) 보고 ID 설정, (2) user_id 부여 시점, (3) BigQuery `user_pseudo_id` 기준 재집계 순서로 확인한다. 해결책은 두 갈래: 첫 페이지부터 user_id를 보낼 수 있으면(로그인 사용자) 그렇게 하고, 아니면 퍼널 분석은 BigQuery에서 `user_pseudo_id` 기준으로 한다.
